元記事: Avid（@Av1dlive）X投稿「How to Build An Agentic OS using Fable 5 (Builder's Guide)」2026年7月7日 翻訳しています。


Fable 5は数時間放置しても走り続け、自分でサブエージェントを呼び出し、一晩で1週間分の作業を片付けられるモデルになりました。ただし従量課金（入力100万トークンあたり10ドル、出力100万トークンあたり50ドル）で、範囲を区切らないと勝手にやりすぎ、間違いを自信満々に主張してきます。プロンプトを1つずつ手で打っているなら、その使い方はもう時代遅れです。この記事は、Fable 5を「思いつきで話しかける相手」から「1日3ドルで雇える従業員」に変える具体的な仕組みを、ファイル単位で示します。


判定基準
次のどれか1つでも当てはまるなら、今日中に着手する価値があります。Claude Codeに週1回以上似たような指示を繰り返している。生成物を毎回自分の目でチェックしないと信用できない。「あとはお願い」と言って安心して席を外せたことが一度もない。


具体的な行動
1. 公式仕様を踏まえた土台（CLAUDE.md）を作る
理由：Fable 5は「法律」には従いますが、お願い口調の「tips」は最適化の過程で無視します。さらに公式ドキュメントには、この後の全工程の前提になる仕様（料金、思考モード、拒否応答の扱い）が定められており、これを踏まえずに書いたスクリプトは後で静かに壊れます。


具体的な手順：
まず以下の5点を前提として組み込みます。
- `max_tokens` は「思考＋本文」の合計に対する上限です。effortをhigh・xhighにするなら64k以上を目安に大きく取らないと、考えている途中で打ち切られます。
- xhighは公式に「30分以上かかる長時間の自律タスク」向けとされています。この記事では後述する「指揮官（コンダクター）」だけがxhighを使い、実行役のモデルはhighより上げません。
- 拒否応答はHTTP 200で返ってきます。安全性の分類器（サイバー攻撃・生物兵器・推論の開示要求など）に引っかかると `stop_reason: "refusal"` が「成功」扱いで返るため、スクリプトは終了コードではなく `stop_reason` を必ず確認する必要があります。
- 「考えた過程を答えの中に書き出して」という指示は、推論開示（reasoning_extraction）の拒否カテゴリを誘発します。既存のプロンプトに「思考過程を見せて」に類する文言がないか点検してください。
- 1ターンが長時間になるのは仕様です。高いeffortでは1リクエストが数分単位、自律実行では数時間に及ぶため、待ち受けはブロッキング処理ではなくcronのような非同期の仕組みにします。


その上で、リポジトリ直下に `CLAUDE.md` を作成し、次の4ブロックだけで構成します。①NEVER（数字か絶対禁止事項で書いた法律）、②DISPATCH（タスクをどのモデルに振るかの表）、③WORDS（「完了」「小さい」などの用語定義）、④DONE（完了判定の手順）。150行以内に収め、「ステップバイステップで考えて」のような指示は書きません（思考は常時オンで、それ自体が課金対象のため）。


コピペ用プロンプト：
plaintext
このリポジトリ直下に CLAUDE.md を作成して。中身は次の4ブロックのみで構成する。
1. NEVER: 数字か「絶対に〜しない」で書いた禁止事項のリスト
   （例: 1コミットで200行を超える変更をしない、auth/billing/migrations/本番設定には無人で触れない、
   自己判断で「完了」と報告しない、存在しない秘密情報や規約を作らない）
2. DISPATCH: タスクの種類ごとにどのモデル・どのeffortを使うかを決める表
3. WORDS: このリポジトリで使う用語（「完了」「小さい」「素早い」など）の定義
4. DONE: 完了判定の手順（機械的に検証できる条件、fresh contextのエージェントによる検証、
   最終判定はbashスクリプトが行う、という順序）
全体を150行以内に収め、「ステップバイステップで考えて」のような指示は含めない。


2. 被害範囲の壁と、最終判定をする関所を作る


理由：自動化を始める前に「どこまでは無断でやっていいか」を宣言しておかないと、暴走したときに止める手段がありません。判定は人間の裁量ではなく、bashスクリプトが機械的に下す必要があります。


具体的な手順：`loop/contract.md` に3つのリストを書きます。「一人で進めていいこと」（ブランチ上のドラフトPR、lint・テストの負債解消など）、「私の承認を待つこと」（認証・決済・マイグレーション、diffが400行を超えるものなど）、「私を起こすこと」（同じ項目で検証が2回連続失敗、安全装置がモデルを勝手に差し替えた、日予算超過、標準の目標が破られた、など）。あわせて `loop/guardrails/verify.sh` を作成し、型チェック・テスト・lintを順に実行して失敗したら止まるようにします。これが今から作るシステム全体の土台になるので、今の時点で手動実行して緑になることを先に確認します。


コピペ用プロンプト：


plaintext
loop/contract.md と loop/guardrails/verify.sh を作成して。
contract.md には「一人で進めていいこと」「私の承認待ちにすること」「私を起こすこと」の
3つの見出しでリストを書く（内容はこのリポジトリの構成を見て提案して）。

3. 指揮官・実行役・検証役を分けた心臓部（ループ）を作る


理由：Fable 5に実際のコード生成までやらせると、1セッションで50万〜100万トークンを消費し、出力単価50ドル/百万トークンで4桁ドルの請求になります。Fable 5は「指揮官」として全体の10〜20%のトークンで100%の意思決定だけを担当させ、実際の作業は安いモデルに振ります。各役割はJSON形式で仕事を受け渡すため、どのモデルをどの役に据えても差し替え可能です。


具体的な手順：4つのプロンプトファイルを用意します。`triage.md`（直近のコミット・issue・CI結果を読み、対応が必要かどうかだけを判定する安いモデル用プロンプト）、`conductor.md`（Fable 5用。コードは書かず、状態・信頼台帳・契約を読んで「実行／保留／様子見」のいずれかとJSON形式の作業指示を1件だけ出す）、`workers/implement.md`（作業指示どおりに次の1手だけを実行する安いモデル用）、`workers/verify.md`（仕様とdiffだけを見て合否を1行で判定する、フレッシュな状態のFable 5）。これらを `loop.sh` で1つのtickとしてつなぎ、各段階のコストをログし、1日の予算を超えたら止まるようにします。


コピペ用プロンプト：
plaintext

安いモデル向けの読み取り専用プロンプト。何もなければ「status: quiet」とだけ出す。
2. conductor.md: Fable 5向け。コードは書かない・ファイルは編集しない。状態と信頼台帳とcontract.md を読み、最も価値が高い1件を選び { "action": "execute|queue|stop", "item", "skill", "spec", "done_when": [...] }というJSONだけを出力する。
3. workers/implement.md: 受け取った作業指示(JSON)どおりに done_when に向けた次の1手だけを実行する。秘密情報や規約が必要なのに存在しない場合は実行を止めて質問を記録する。

4. 信頼を数字で管理する台帳を作る
理由：「信頼が育ったら自動化する」は精神論のままでは機能しません。何回実行して何回成功したかをファイルに記録し、しきい値で機械的に判定する必要があります。信頼は「ループ全体」にではなく「スキール（作業の種類）ごと」に付与します。


具体的な手順：
`loop/scripts/trust-log.sh` を作成し、TSV形式でスキルごとの実行回数と成功回数を記録します。判定基準は、20回以上実行かつ成功率95%以上なら「auto」（無人で出荷可）、10回未満または成功率90%未満なら「watch」（下書きのみ）、それ以外は「queue」（人間の確認待ち）とします。
降格は自動かつ標準エラー出力に出るようにしておくと、cronのメール通知で気づけます。よくある定型作業（lint負債の解消、不安定テストの修正、依存関係の更新、issueの仕分け）は `loop/skills/` にそれぞれ1ファイルとして登録し、全スキルは最初「watch」から始めます。


コピペ用プロンプト：
plaintext
loop/scripts/trust-log.sh を作成して。
使い方は3パターン: trust-log.sh <スキル名> <pass|fail>（記録の追加）、
trust-log.sh --render（全スキルの実行回数・成功回数・成功率・判定を一覧表示）、
trust-log.sh --tier <スキル名>（そのスキルの現在の判定だけを返す）。
判定基準は、実行20回以上かつ成功率95%以上で auto、実行10回未満または成功率90%未満で watch、
それ以外は queue。fail を記録した結果 watch に降格した場合は、標準エラー出力に
ALERTメッセージを出す。データは memory/trust.tsv にタブ区切りで保存する。


5. 終わった仕事を「監視対象」として台帳に残す
理由：一度しか検証しなかった目標は、日付が付いただけの推測に過ぎません。完了した作業も日次で再検証し続けないと、静かに壊れても誰も気づけません。


具体的な手順：
完了した作業ごとに `goals/<名前>.md` を作り、`predicate`（終了コード0で成立とみなす検証コマンド）、`born`（作成日）、`source`（何の作業から生まれたか）、`status`、`on-violation`（破られたときの対応方針）、`retire-when`（引退させる条件）を記録します。predicateは形容詞では書けません。
bashで判定できないものは目標にしないというのが原則です。
これらを毎日読み込んで実行し、結果を `memory/goal-ledger.tsv` に記録して、破られていればその目標ファイルを「VIOLATED」に書き換える `verify-goals.sh` を作成し、1日1回のループとして起動します。
この見張り役は異常を検知するだけで、修理は通常のパイプラインに任せます。


コピペ用プロンプト：
plaintext

終了コード0なら status を satisfied に、last-pass を今日の日付に更新する。
0以外なら status を VIOLATED に書き換え、失敗としてカウントする。

1件でも VIOLATED があれば、そのファイル名を表示して終了コード1で終わる。


6. 予算を自己防衛させ、運用に乗せる
理由：1日のコストは「tick数×トリアージ費用」＋「実行が発生した回数×（指揮官＋実行役＋検証役の費用）」で決まります。実行間隔を半分にすればコストの下限は倍になります。上限は後から気づくものではなく、先に数字で決めて自動的に止まる仕組みにしておくべきです。


具体的な手順：
`loop/scripts/log-cost.sh`（各段階の費用をログに追記）と `loop/scripts/cost-check.sh`（当日の合計が予算を超えていれば止める）を作成します。
ループ内のeffortはhighを超えないというルールを徹底し、xhighは単発のレビューだけに使います。
Makefileに `tick`（1回実行）・`queue`（保留中の一覧）・`trust`（信頼台帳の表示）・`audit`（週次コストレポート）・`goals`（目標の再検証）をまとめ、平日朝に `loop.sh` を、毎日決まった時刻に `verify-goals.sh` をcronで自動実行します。
導入は一気にではなく、4つのオプションループ（複数の安いモデルで多数決してからFable 5を起こす「クォーラム」、数値指標を単調改善させる「ラチェット」、対立する2つのループでコードを鍛える「スパーリング」、週次で失敗から新しい法律を提案する「コンポスト」）は、それぞれの導入条件が実際に発生してから足します。

警告
effortの設定を誤ると、thinkingと応答トークンの合計だけで簡単に高額請求になります。`max_tokens` を明示的に大きく確保していないと、考えている途中で打ち切られて不完全な出力が返ります。信頼ティアが「auto」に達したスキルは、人間の確認なしにコミットとPR作成まで行います。`verify.sh` の中身が薄いと、壊れたコードがそのまま外に出ます。Fable 5の拒否応答はHTTP 200で返るため、終了コードだけを見るスクリプトは「拒否された」ことに気づかず「成功した」と誤認します。`stop_reason` の確認を必ず組み込んでください。認証・決済・マイグレーション・本番設定に無人で触れさせない、という壁（CLAUDE.mdのNEVER）を先に書かないと、後から止める手段がありません。


まとめ
Fable 5には「指揮官」の役割だけを与え、実際の作業は安いモデルに任せる設計にすると、全体のコストが1桁下がります。憲法（CLAUDE.md）・壁（contract.md）・関所（verify.sh）を最初に作ってから自動化を始めます。信頼台帳（trust.tsv）と目標台帳（goal-ledger.tsv）という2つの帳簿が、今どこまで手放していいかを機械的に教えてくれます。導入はおよそ30日かけて、毎日手で回す→cron任せの下書き→無人出荷→改善提案の承認、という順に権限を段階的に引き上げます。予算管理と拒否応答の扱いを間違えると、静かにコストが膨らむか、静かに失敗が握りつぶされるかのどちらかが起きます。

第二「Bookmark these 8 builds before you forget」（忘れる前にブックマークしろ）や「今夜20分でこれを証明しよう」といった行動喚起の文言は、情報商材的な緊急性演出の定石でもあります。実際にはこの記事を今夜読まなければ機会を逃す、というような技術的な理由はなく、いつ着手しても効果は変わりません。読者の離脱を防ぐための煽りである可能性は割り引いて読む必要があります。


第三「トリアージ0.01ドル、指揮官0.35ドル、実行役0.10ドル、検証役0.40ドル」「20回以上かつ成功率95%でauto」といった具体的な数字は、著者自身の環境での見積もりか経験則であり、第三者による検証や再現実験の裏付けは示されていません。著者本人のリポジトリという事実上n=1の結果を一般則として提示している可能性があり、読者自身のリポジトリでは全く違うコスト構造や失敗率になり得ます。しきい値である20回・95%という数字自体にも、なぜその数字なのかという根拠は書かれていません。


第四「システムを作れば信頼して手放せる」という建前に対し、実際に安全性を担保しているのはFable 5そのものではなく、`verify.sh` の中身（結局は通常のtypecheck・test・lint）と、CLAUDE.mdに書く禁止事項の質です。つまりこの記事の価値の大部分は「良いテストと良いレビュー基準をどう書くか」という、AI以前からのソフトウェア工学の基本に依存しており、それをFable 5向けの装いで再提示しているとも読めます。AIが賢くなったから安全になったのではなく、人間が先に安全装置を書いたから安全になっている、という順序を見誤らないほうがよいでしょう。

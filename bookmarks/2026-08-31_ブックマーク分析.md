## 1. 権限モードと安全設計

今期最大の変化。8/14からPro/Max/TeamでAutoモードが既定の許可モードになった。分類器が危険コマンドの89%を検出（手動承認は14%）。同時に、落合式・24時間エージェント設計の両記事が「自律化するのは工程であって権限ではない」と繰り返している。

### 🛠 環境改善・向上

1. **[P1] `defaultMode` の設定を見直す**：現在 `~/dotfiles/claude/settings.json` に `"defaultMode": "acceptEdits"` をピン留めしている。公式告知は「すでにデフォルトモードを設定済みの場合はそのまま」なので、**この設定がある限りAutoモードの分類器による危険コマンド検出は効いていない可能性が高い**。ピン留めを外してAutoに委ねるか、acceptEditsを維持するかを決める。値の正確な仕様は公式ドキュメントで裏取りしてから変更すること（CLAUDE.mdの「公式確認してから実装」ルール）。→ `doc-verifier` エージェントで確認するのが早い。（元記事：0811-0818 #5）

2. **[P2] denyリストを「消す・送る・払う・本番変更」の4カテゴリで棚卸しする**：現在のdenyは `rm -rf` / `git push --force` / `.env` の読み書きの4件のみ。落合式記事の線引き（AIに任せるのは「考える・作る・テストする」、人間が承認するのは「消す・送る・払う・本番を変える」）に照らすと、**「送る」（外部送信・SNS投稿）と「払う」が未カバー**。例えばGoogle Drive アップロードスクリプトやDiscord送信系は無条件で通る状態。（元記事：0811-0818 #2）

3. **[P2] 「文章での禁止」を「仕組みでの禁止」に格上げする**：CLAUDE.mdに書いたルールは方針であって強制力がない、という指摘。現環境ではすでにWebFetch禁止をPreToolUseフックで `exit 2` させており、この形が正解。同じ発想で、まだ文章ルールのままの項目（例：「git pull前にgit statusを確認する」）をフック化できないか検討する。（元記事：0811-0818 #9）

### 📚 学習

4. **[P2] 「自律化するのは工程であって権限ではない」**：寝ている間に動かす＝確認を全部オフ、ではない。落合陽一の公開環境も既定は毎回確認。自動承認モードは上級者向け・自己責任と明記されている。安全な半自動を積み上げる方が結果的に早い、という考え方。（元記事：0811-0818 #2）

## 2. マルチエージェント設計・視点分離

19件中5件がこのテーマ。今期の主軸。核心は「1体に全部見せない。1体には1つの視点だけ渡す」。

### 🛠 環境改善・向上

5. **[P1] レビュー用サブエージェントを「視点1つ」で作る**：現在のエージェントは `doc-verifier` / `my-info-extractor` / `seo-researcher` の3体で、いずれも調査・抽出系。**批判・検証担当がいない**。まず1体だけ、`fact-checker`（事実と数字の誤りだけを探す。改善提案はしない）を `~/dotfiles/claude/agents/` に追加する。公式推奨は3〜5体からで、「3体の集中したエージェントの方が5体の曖昧なエージェントより有効」。（元記事：0811-0818 #2）

6. **[P2] 「反対意見だけを担当するAI」を1体入れる**：賛成・反対・審判の3体構成。実施済みリストの未実施項目「対立検証パターン（Opponent Processor）」がまさにこれ。例えば社会保険の手続き定義ファイル（`hr-shahou-register`）を作るときに、「この定義で漏れる申請パターンだけを探す」役を立てると、web調査の取りこぼしが拾える。（元記事：0811-0818 #2、0817-0824 #1）

7. **[P2] レビュー結果を「そのまま適用させない」一文を入れる**：指摘を全部そのまま直させると、矛盾する修正が入って前より悪くなる。「重複・誤検出・矛盾を整理してから修正し、修正後に再検証する」を必ず挟む。（元記事：0811-0818 #2）

### 📚 学習

8. **[P2] 「一致ではなくズレを見る」**：複数AIを使う目的は多数決ではない。5体中1体だけが別の文献を持ってきた、前提そのものを疑った——その**ズレが新しい着想の起点**になる。逆に5体が同じことを言っても、同じ二次情報を参照しているだけの可能性がある。（元記事：0817-0824 #1）

## 4. 長時間・自律運用のハーネス設計

このテーマだけで元記事2本（合計3万字超）。現環境はすでに systemd タイマーで週次ブックマーク収集を無人運用しているので、**そのまま適用できる指摘が多い**。

### 🛠 環境改善・向上

13. **[P1] 状態を会話ではなくファイルへ持たせる**：長時間運用でセッションが落ちることを前提にし、`job_id` / `status` / `current_step` / `completed_steps` / `retry_count` / `last_error` をJSONで外部保存する。**現環境の弱点がここ**：`x-bookmark-weekly` は失敗すると最初からやり直しで、どこまで終わったかが残らない。5月のタイムアウト失敗（status=143）も、状態ファイルがあれば途中から再開できた。（元記事：0811-0818 #9）

14. **[P2] 冪等性キーで二重実行を防ぐ**：`bookmark-weekly:2026-W35` のようなキーを持たせ、completedなら何もしない。現在の重複防止は「処理済み235件をスキップ」というアプリ内ロジックに依存していて、ジョブ単位の重複防止はない。Google Driveアップロードなど副作用のある処理には必須。（元記事：0811-0818 #9）

15. **[P2] リトライを「種類×上限」で設計し直す**：現在の systemd 設定は `Restart=on-failure` / `RestartSec=600` / `StartLimitBurst=3` で回数上限はあるが、**エラーの種類を区別していない**。認証エラー・権限不足・入力不備は再試行しても無駄なので即停止すべき。再試行してよいのは通信エラー・レート制限・タイムアウト・5xxのみ。（元記事：0811-0818 #9）

16. **[P2] 各工程に「完了条件」を明文化する**：「ニュースを調べる」のような曖昧なタスクは終了判定できない。入力・出力・完了条件を工程ごとに定義すると、AI自身の「できました」ではなくシステム側で判定できる。既存スキルのSKILL.mdに完了条件セクションを足すのが最小の一歩。（元記事：0811-0818 #9）

17. **[P3] 本番投入前チェックリスト15項目を持っておく**：一意のジョブID／二重実行防止／状態の外部保存／途中再開／完了条件／出力形式の検証／リトライ上限／タイムアウト／コスト上限／読み書き権限の分離／削除・公開・課金の承認制／連続実行の検知／失敗通知／実行ログ／緊急停止。**一つでも答えられなければ完全自動へ進む段階ではない**。（元記事：0811-0818 #9）

### 📚 学習

18. **[P2] 「決定的な処理」と「非決定的な処理」を分ける**：同じ入力なら同じ結果になるべき処理（API取得・重複削除・JSON保存・通知）はコードへ。文脈を読んで判断する処理（重要度評価・要約・分類）だけAIへ。AIの担当範囲が狭いほどテストと改善が簡単になる。（元記事：0811-0818 #9）

19. **[P2] 圧縮された会話に依存しない**：Compactionは要約なので必ず情報が落ちる。特に消えやすいのは「なぜその設計を選んだか」「却下した候補」「未完了の作業」「正確な数値やID」「承認した内容」。**これらは会話の外へ出す**。現環境の basic-memory ＋ auto-memory がまさにこの役割なので、運用を続ける根拠になる。（元記事：0811-0818 #9）

20. **[P3] 実行環境の使い分け**：`/loop`＝セッションが開いている間の短時間監視・試作（定期タスクは7日で失効）／Claude Routines＝PCを閉じても動く定期実行（最小間隔1時間・リサーチプレビュー）／Modal・Trigger.dev＝AI判断が不要な処理／Agent SDK＝自分のアプリに組み込む／Managed Agents＝実行基盤ごと任せる。**現環境の systemd タイマーは「自前のRoutines」に相当**する位置づけ。（元記事：0811-0818 #9）

21. **[P3] 最初は「1時間・1体・1業務」で作る**：実行1時間以内、エージェント1体、業務1つ、外部書き込みは下書きのみ、再試行2〜3回、公開前は人間承認。この順で段階的に広げると、壊れた工程を特定できる。（元記事：0811-0818 #9）

## 今週のピックアップ3選

自動化とエージェントは別物
Zapier、Make.com、IFTTT のような自動化ツールを試したことがある人は多いと思います。フォームが送信されたらテンプレメールが飛ぶ。Slack でメンションされたら Notion にタスクが作られる。固定のトリガーで、固定の処理が走る、というやつです。
便利です。ただ、これと「AI エージェント」はやっていることが根本的に違います。
新規リードからの問い合わせメールを例にしましょう。
自動化が動くと：あらかじめ用意したテンプレメールが返信されます。「お問い合わせありがとうございます。3 営業日以内にご連絡します」みたいな文面が、相手に届きます。
エージェントが動くとどうなるか：まず CRM を見て、この会社と過去にやり取りがあったかを確認します。過去メールを読んで、文脈を引き継ぎます。会社の事業内容を軽く調べて、何のサービスを欲しがっていそうかを推測します。その上で、パーソナライズされた初回メッセージを下書きします。相手のタイムゾーンを見て、開封されやすい時間に送信予約をします。3 日後に「まだ返事がなければフォローアップ」のタスクを自分でカレンダーに入れます。
同じトリガー (新規メール受信) です。やっている内容は完全に別物です。
固定スクリプトと、状況を読んで判断するエージェント。この差は、AI を呼ぶか呼ばないかというより、ワークフローの主語が AI か人か、というところで分かれます。Zapier 系の自動化は、人がワークフロー全体を設計して、AI を「文章生成のサブ処理」として呼ぶ構造になります。エージェントは AI 自身がワークフローを進めて、必要なときだけ人を呼ぶ構造になります。
主語が違うと、自動化できる業務の天井がまったく別のところに上がります。
では、エージェントが judgment を発揮するための「構造」とは何でしょうか。次の章で見ていきます。
Ambient Agent を成立させる 4 コンポーネント
経営者の事務オペレーション層を引き受けるエージェントは、4 つのコンポーネントで成立します。
Claude (判断層)。状況を読む、業務文脈を当てる、適切な行動を決める、というエージェントの中核です。本記事では Anthropic の Claude を使います。Claude API でもいいですし、Claude Code から動かしてもかまいません (本記事は Claude Code 派です。理由は第 7 章で扱います)。
CLAUDE.md (業務文脈層)。ビジネスのことを全部 1 ファイルに書きます。会社の事業内容、動いている案件、メールのトーン、AI に任せていい判断と人間に必ずエスカレーションする判断の境界線、今週の優先事項。Claude Code はセッション開始時に CLAUDE.md を自動で読み込んで、システムプロンプトに注入します。プロジェクトルートの CLAUDE.md か、ユーザーレベルの ~/.claude/CLAUDE.md に置きます。
MCP Servers (ツール接続層)。Claude が実際の業務ツールに繋がるための配管です。Gmail、Google Calendar、Notion、Stripe、Slack、Filesystem。6 種類くらい繋ぐと、経営の事務オペレーションはほぼ届く範囲に入ります。MCP がないと、エージェントは判断はできても行動できません。
Skills + cron (起動 + 配線層)。元記事はここを N8N で組みますが、本記事は Claude Code の Skills と cron に置き換えます。Skills は .claude/skills/<name>/SKILL.md のファイル 1 枚で 1 つの業務を定義する仕組み。cron は OS の標準スケジューラで、claude -p '/skill-name' のヘッドレスモードで起動します。これだけで「人が起動しなくても、時間がくれば AI が業務を回す」設計になります。
この 4 つが揃って初めて、Claude エージェントは「呼べば動く」状態から「先に動く」状態に変わります。チャットを開いて指示する代わりに、AI 側がイベント (時間、メール受信、ファイル変更) を見て、必要なタイミングで動き、判断が必要なときだけ人を呼ぶ。これが Ambient Agent (チャット起点ではなくイベント起点で動くエージェント) の最も具体的な実装例です。
主語が人から AI に渡る、と言ってもいいです。Human with AI tools (経営者が AI を呼ぶ) と AI Agent with Human (AI が必要なときに経営者を呼ぶ) は、見た目は似ていますが自動化の天井が違うところに移ります。
元記事は N8N を起動エンジンとして紹介していますが、Claude Code 自体を起動エンジンに据えると、シンプルかつ高性能になります。詳細は第 7 章で扱います。
では、業務文脈 (CLAUDE.md) は具体的に何を書くのか、見ていきましょう。
CLAUDE.md に業務のすべてを 1 枚で書く
CLAUDE.md は、AI のための業務マニュアルです。新人スタッフを採用したときに渡す業務ガイドラインを、毎週月曜に 5 分で更新する、くらいの位置づけで書きます。
書く内容は 6 ブロックです。
Business Identity (会社のアイデンティティ)。会社名、事業内容、顧客像、収益モデル、フェーズ、月次売上。月次売上は毎月更新するのが理想です。エージェントが判断するときの「うちはこのフェーズ」の前提が変わります。
Active Clients (動いている顧客)。クライアント名、サービスタイプ、月額 (MRR)、現状、次のアクション。動いている顧客が変わったらここを更新します。
Communication Standards (コミュニケーション基準)。メールのトーン、返信時間の約束、絶対言わない表現、メール冒頭の型、メール末尾の型。エージェントがメール下書きを作るとき、ここを基準にします。
Decision Authority (判断権限)。これが 6 ブロックの中で一番大事です。AI が自走していい領域と、必ず人間にエスカレーションする領域を、はっきり分けて書きます。この境界線を間違えると、AI が何もしないか、判断してはいけない判断をします。
Quality Standards (品質基準)。自社にとって「良い仕事」とは何かを言葉にします。納品物の見栄えなのか、運用継続率なのか、顧客の業務が実際に変わったかなのか。
This Week's Focus (今週の焦点)。今週の優先事項を 3 行くらいで書きます。これを毎週月曜に更新すると、6 ワークフロー全部の判断が今週の焦点に沿うようになります。
ここで重要なのは、業務文脈を AI に渡せるかどうかが、エージェントの判断品質を決める、ということです。プロンプトを長く書くより、CLAUDE.md を丁寧に書く方が、はるかに効きます。
実際にどう書くか、1 人会社経営者の例で全体を書いてみます。コピペして自社の情報に差し替えれば、明日から動かせます。
markdown
# Business Management Agent -- CLAUDE.md
## Business Identity
会社名: 合同会社○○
事業内容: 中小企業向けの業務改善コンサルティング (現場 1 体型支援)
顧客像: 従業員 30-100 名規模の地方の製造業・卸売業
収益モデル: 月額顧問契約 + プロジェクト報酬
フェーズ: 立ち上げ 2 年目
月次売上: ¥1,500,000 (毎月更新)
## Active Clients
A 株式会社 (製造業): 月額 ¥300,000 / 状況: 業務マニュアル整備中 / 次のアクション: 5 月末に第 1 弾納品
B 製作所 (卸売業): 月額 ¥250,000 / 状況: 来月から経理 DX 案件開始 / 次のアクション: キックオフ MTG 設定
C 工業 (製造業): 月額 ¥200,000 / 状況: 月次レポート定期化 / 次のアクション: 5 月分レポート提出
## Communication Standards
メールのトーン: 簡潔・直接的・丁寧
返信時間の約束: 24 時間以内 (営業日)
絶対言わない表現: 「お忙しいところ恐れ入りますが」「何卒よろしくお願い申し上げます」(冗長な定型句)
メール冒頭: 「○○様 お世話になっております。△△ (自分の名前) です。」
メール末尾: 「よろしくお願いします。」
## Decision Authority
AI が自走していい領域:
- スケジュール調整の打診メール下書き作成 (送信は人間が承認)
- 既存のドキュメントからのレポート生成
- Notion の社内プロジェクト進捗ステータス更新
- 内部システム間のデータ転送と整形
- 顧客向けではない内部メモの作成
必ず人間にエスカレーションする領域:
- 外部宛メールの送信実行
- 金融取引 (請求書発行・支払い実行)
- クライアントへの新規コミットメント (納期約束・追加業務の受諾)
- 契約条件の変更
- 公開コンテンツ (SNS / ブログ) の投稿
## Quality Standards
「良い仕事」= 顧客の業務が実際に変わったか。納品物の見栄えではなく、運用 1 ヶ月後に顧客が継続的に使っているかで判定する。
## This Week's Focus (毎週月曜に更新)
- A 株式会社の第 1 弾納品準備 (金曜までに最終確認)
- B 製作所のキックオフ MTG 日程確定 (今週中)
- C 工業からの追加問い合わせ対応 (新規案件化の可能性)
これを ~/.claude/CLAUDE.md か、プロジェクトディレクトリの CLAUDE.md に保存します。Claude Code はセッション開始時に自動で読み込みます。あとは MCP を繋いで、Skills を書いて、cron でスケジュールするだけです。
「業務マニュアルを書く」というと身構えますが、上の例だと A4 1 枚に収まります。最初に 30 分で書いて、毎週月曜に 5 分で更新するくらいで十分機能します。新人スタッフに渡すマニュアルと同じ感覚で大丈夫です。
個人的には、まず Business Identity と Decision Authority の 2 ブロックだけを書いて、残りは運用しながら埋めていくのを推します。Decision Authority が最初から書けていると、AI が「やっていいこと」と「人に確認すること」の境界をつかんでくれるので、変な暴走が起きません。
では、Claude エージェントはどのツールに繋ぐのか。次の章で MCP を見ていきます。
6 種類の MCP がエージェントに手と目を与える
MCP (Model Context Protocol) は、AI が外部のツールにアクセスするための共通プロトコルです。MCP がないと、エージェントは判断はできても、メールを読めない、カレンダーを見られない、Notion を更新できない、という状態になります。
経営のオペレーションには、6 種類繋ぐと届く範囲がほぼカバーできます。順に紹介します。
Gmail MCP。メールの読み込み、種類別の仕分け、下書き作成、特定キーワードの監視。元記事では @modelcontextprotocol/server-gmail (コミュニティ版) が使われていますが、Google が公式リモート MCP サーバー (gmailmcp.googleapis.com) を提供しているので、これからは公式版を使うのが安全です。OAuth 2.0 認証で繋ぎます。
Google Calendar MCP。予定の読み込み、新規予定の作成、リマインダー設定、スケジュール衝突の検知、ミーティング前のブリーフィング準備。これも Google 公式リモート MCP サーバー (calendarmcp.googleapis.com) が出ています。
Notion MCP。プロジェクト DB の読み書き、顧客レコードの更新、タスク進捗の管理、ライブデータからのレポート生成。Notion 公式パッケージ @notionhq/notion-mcp-server (npm) を使います。GitHub は makenotion/notion-mcp-server。
Stripe MCP。売上のモニタリング、決済失敗の通知、MRR トレンドの追跡、月次決算サマリの生成。Stripe 公式の @stripe/mcp パッケージか、リモートサーバー (https://mcp.stripe.com、OAuth 経由) を使います。読み取り中心なら、必ず Restricted API Key (rk_ で始まるキー) を発行して権限を絞ります。
Slack MCP。チャンネルへの自動投稿、ワークフロー完了の通知、メンション対応。@modelcontextprotocol/server-slack (npm) が長らく標準でしたが、2025 年 5 月にアーカイブされました。機能的にはまだ動きますし、@zencoderai/slack-mcp-server のようなメンテナンス版フォークもあります。
Filesystem MCP。ローカルファイルの読み書き、Obsidian vault へのアクセス、レポートや生成コンテンツの保存。@modelcontextprotocol/server-filesystem (npm) を使います。npx -y @modelcontextprotocol/server-filesystem /path/to/directory で起動できる手軽さがあります。
最初から 6 個全部繋ぐ必要はありません。Gmail と Calendar の 2 個から始めて、業務が動き出したら順次追加するのが現実的です。1 つ繋ぐとできることが目に見えて増えるので、自分で「次これも欲しい」となります。
繋ぐ設定は ~/.claude/claude_desktop_config.json か、プロジェクトの .claude/mcp.json に書きます。Gmail / Calendar は Google 公式リモート MCP の OAuth フロー、Notion は API Key、Filesystem と Stripe は npx -y の 1 行で動かせる、という温度差があります。Layer A の経営者は技術担当に「この 6 個繋いでおいて」と依頼するだけで十分機能します。
ツールが繋がったら、その上で具体的に何を動かすか。次の章で 6 つの Skills を見ていきます。
6 ワークフローを Skills として書く
ここからが本記事の実装パートです。元記事で紹介されている 6 つの業務管理ワークフローを、Claude Code Skills として書きます。
Claude Code Skills は、.claude/skills/<name>/SKILL.md のディレクトリ構造で定義します。SKILL.md は YAML フロントマター (name と description) + Markdown 本文の 1 ファイル。Claude はセッション開始時に全 Skill の name と description だけをプリロードして、必要と判断したときに本文をロードします (progressive disclosure)。手動で起動するときは /skill-name の slash command が使えます。cron でヘッドレス起動するときは claude -p '/skill-name' で呼び出します。
6 つの業務完成品 (毎朝のブリーフィング、メール仕分け、顧客健康診断、月次決算、プロジェクト進捗、週次振り返り) を、それぞれ 1 つの Skill として書きます。
Workflow 1: morning-briefing (毎朝のブリーフィング)
起動は平日朝の cron。入力は前日夕方以降のメール + 今日の予定 + プロジェクト状況 + Stripe の昨日からの変化。出力は、URGENT (午前中までに対応が必要なもの) / 今日のスケジュール (各ミーティングの準備メモ付き) / 今日対応が必要なメールの優先順 / プロジェクトのアラート / 売上のアップデート / 今日の 1 つの焦点。出力先は ~/vault/daily-briefings/[DATE].md に保存して、Slack の #daily-briefing チャンネルにサマリを通知します。
朝、PC を開いたときに、完成した運営の全体像が待っている状態が作れます。メールと Slack と Notion を順に開いて、自分で要点を抽出する作業が消えます。
Workflow 2: email-triage (メール仕分けと下書き)
起動は営業時間中の 2 時間ごとの cron。入力は過去 2 時間の未読メール (Gmail MCP 経由)。出力は 5 段階の分類: CLIENT URGENT (2 時間以内に返信が必要) / CLIENT STANDARD (24 時間以内に返信) / PROSPECT (新規見込み顧客) / VENDOR/ADMIN (急がない) / AUTOMATED (返信不要)。CLIENT URGENT と PROSPECT には下書きを作成します。下書きは、CRM の相手レコード + 過去のメールスレッド + CLAUDE.md の Communication Standards を踏まえて、相手の論点全部に応答し、次のアクションを明示する内容で組み立てます。
ここで重要なのは、Skill は下書きを作るだけで、送信はしないことです。Decision Authority で「外部宛メールの送信」は人間エスカレーション領域に置いてあります。下書きを Slack に通知して、人間がレビューして送信ボタンを押す、という運用にします。
メール仕分けに毎日 45 分使っていた人が、レビューと送信の 10 分だけで済む状態になります。
Workflow 3: client-relationship-monitor (顧客の様子を見る)
起動は週初めの cron。入力は Notion の顧客レコード全部。出力は各顧客を HEALTHY / ATTENTION NEEDED / AT RISK の 3 段階で評価して、ATTENTION NEEDED にはチェックイン用の下書きを作成、AT RISK は緊急アラートを Slack に飛ばします。アップセル機会 (顧客の利用状況と表明されたゴールから、自然な拡張の余地) も検出します。
顧客解約は早期発見できれば救えます。AT RISK のサインを週初めに拾えれば、その週のうちに会話を持って関係を立て直せます。手遅れになってから気づくと、もう決定済みです。
Workflow 4: revenue-tracking (月次決算)
起動は月初の cron (毎月 1 日 8 時など)。入力は前月の Stripe 取引 + ローカルの経費ファイル + CLAUDE.md の売上目標。出力は売上サマリ (MRR / 新規 MRR / 拡張 MRR / 解約 MRR / 純増) / 顧客別売上 / 経費サマリ (カテゴリ別と前月比) / 予測 (現在のペースでいくと四半期 / 年間でどこに着地するか) / 推奨アクション 1 つ + コスト削減機会 1 つ。
月初の 1 日が、数字を集める作業ではなく、出来上がったレポートを読んで判断する時間に変わります。
Workflow 5: project-status-updater (プロジェクト進捗自動更新)
起動は continuous (Filesystem MCP で daily-notes ディレクトリを監視 + 5 分間隔の cron で更新検知)。トリガーは、自分の日次メモに DONE: [プロジェクト名] -- [タスク名] と書いたとき。動作は、Notion の該当プロジェクトレコードを開いて、タスクに完了マーク + タイムスタンプを付ける。依存しているタスクがあれば READY 状態にする。現フェーズの全タスクが完了していればプロジェクトを次のフェーズに進める。進捗率を再計算して更新する。Slack に「[プロジェクト名] -- [タスク名] 完了。プロジェクト全体は [X]%」と通知する。
「やったよ」を日次メモに 1 行書くだけで、プロジェクト DB が勝手に追従します。ステータス更新の手作業がゼロになります。
Workflow 6: weekly-review (週次振り返り)
起動は週末の cron。入力は過去 7 日の日次メモ + プロジェクトの今週のステータス変化 + メール仕分けログ + 売上 + Workflow 3 の顧客レポート。出力は、今週前進したこと (具体的なプロジェクト・顧客・指標 + 改善の原因) / 今週動かなかったこと (停滞の正直な評価 + 最も可能性の高い原因) / 今週繰り返し出現したパターン 1 つ (ポジティブか要対応か) / 来週の優先事項 3 つ (ビジネスインパクト順、各項目に「なぜ重要か」と「次の具体アクション」) / 今決めるべき 1 つの決定 (持っている情報 + 1 週間延期したら何が起きるか)。
週次レビューが上手く回せると、日々のオペレーションでは見えないパターンが浮かびます。普通にやると 90 分かかる作業が、出来上がったレポートを読む 15 分に変わります。
SKILL.md の最小サンプルを、Workflow 1 で示します。これだけのファイルです。
yaml
---
name: morning-briefing
description: 平日朝に、前日夕方以降のメール / 今日の予定 / プロジェクト状況 / 売上を集約して、URGENT / スケジュール (準備メモ付き) / メール優先順 / プロジェクトアラート / 売上アップデート / 今日の 1 つの焦点を出力する Skill

# Morning Briefing Workflow
CLAUDE.md を読み込んだ上で、以下を実行します。
## Step 1: 情報収集
- Gmail MCP: 前日 17 時以降のメール全て
- Calendar MCP: 今日の予定 (外部ミーティングは相手の過去メール + Notion の顧客レコード参照)
- Notion MCP: 進行中の全プロジェクト (overdue / 期限接近を抽出)
- Stripe MCP: 昨日からの取引とアラート
## Step 2: 出力
以下のフォーマットで `~/vault/daily-briefings/[YYYY-MM-DD].md` に保存。
- URGENT (午前中対応必須): [リスト]
- 今日のスケジュール: [準備メモ付き]
- メール優先順: [今日返信必要なもの]
- プロジェクトアラート: [要注意なもの]
- 売上アップデート: [主要数字]
- 今日の 1 つの焦点: [今日いちばん大事な仕事]
## Step 3: 通知
Slack の #daily-briefing にサマリ投稿。
これで 1 つの Skill になります。残り 5 つの Skill も、同じ構造で書いていきます。
1 つの SKILL.md に必要なことは全部書いて、起動条件 (cron) はあとで cron に書きます。最初は morning-briefing 1 つから始めて、週 1 つずつ追加していくと、2 ヶ月後には 6 つのワークフローが全部回っている状態になります。
個人的には、最初に組むなら morning-briefing 一択だと思っています。朝の運営全体像が出来上がっていることの体感変化が一番大きくて、ここで効果を感じると残り 5 つを書く動機が湧きます。逆に email-triage から始めると、メール下書きの精度調整に時間を取られて、効果が見える前に疲弊しがちです。
6 つのワークフローは、見方を変えると 6 つの業務完成品です。毎朝のブリーフィング、メール下書きセット、顧客健康診断レポート、月次決算サマリ、プロジェクト進捗の最新状態、週次振り返り。それぞれが「1 つの仕事が完了した状態」を作ります。経営者が「今日のブリーフィングどこ?」「メール下書きある?」と探す必要なく、毎朝決まった場所に出来上がって待っています。
では、これら 6 つの Skills を、何が起動して回すのでしょうか。元記事は N8N を使いますが、本記事は次の章で別の設計を提示します。
Claude Code 自体を起動エンジンにする
元記事は起動エンジンに N8N (外部のワークフロー自動化ツール) を選んでいます。N8N でスケジュールを組んで、Claude API を呼んで、出力を処理して、Slack に通知する、という流れです。
本記事はここを完全に置き換えて、Claude Code 自体を起動エンジンにします。N8N のような外部ツールを挟む必要がありません。
N8N がやっていることは、コンポーネントに分解できます。スケジューラ、トリガー、データの受け渡し、API 呼び出し、出力先への書き込み、ログ。これら全部、Claude Code エコシステム内で代替できます。
スケジューラの役割 → cron (Mac なら launchd、Linux なら systemd でもいい)
トリガーの役割 → ヘッドレスモード claude -p '<prompt>' で呼ぶだけ
データの受け渡し → SessionStart 時に CLAUDE.md と Skills が自動でロードされる
Claude API 呼び出し → 不要 (Claude Code 自体が動く)
出力先への書き込み → Filesystem MCP + Skill 内で完結
ログ → セッションログ + Slack MCP 通知
6 つの Skills を cron に登録すれば、それだけで起動が回ります。crontab の中身はこれだけです。
bash
0 6 * * 1-5 cd ~/business && claude -p "/morning-briefing"
0 9,11,13,15,17 * * 1-5 cd ~/business && claude -p "/email-triage"
0 7 * * 1 cd ~/business && claude -p "/client-relationship-monitor"
0 8 1 * * cd ~/business && claude -p "/revenue-tracking"
*/5 * * * * cd ~/business && claude -p "/project-status-updater"
0 19 * * 0 cd ~/business && claude -p "/weekly-review"
6 行です。これだけで、平日朝のブリーフィングから、営業時間中 2 時間ごとのメール仕分け、週初めの顧客健康診断、月初の決算、5 分間隔のプロジェクト進捗更新、週末の振り返りまで、全部回ります。N8N に GUI で設定するワークフローも、DigitalOcean droplet の構築も、Gmail webhook の設定 (元記事だと初回 30-45 分かかると書かれています) も、いりません。
なぜ Claude Code 起動エンジンの方が性能が出るのか、4 つの軸で書きます。
(a) judgment の品質。N8N の Trigger Node は固定配線です。同じトリガーには必ず同じ処理が流れます。Claude Code は AI が状況を読んで判断を発揮できます。同じ「新規メール受信」のトリガーでも、Skill が業務文脈を踏まえて「これは既存顧客からの急ぎ」「これはベンダーからの請求書」「これは AT RISK 顧客のエスカレーション」と読み分けて、別の処理に流せます。N8N で同じことをやろうとすると、分岐ノードを大量に書く羽目になります。判断のための文脈が、N8N の JSON config では渡しきれません。
(b) コンテキスト統合の深さ。Claude Code は起動時に CLAUDE.md と Skills が自動でロードされます。This Week's Focus を更新するだけで、6 ワークフロー全部の判断が今週の優先事項に沿うようになります。N8N + JSON config の API 呼び出しは、毎回コンテキストをパラメータで渡す必要があります。コンテキストの一部だけが各ノードに流れるので、ワークフロー全体で業務文脈が統合されにくい構造です。
(c) 自己進化。Claude Code Skills は、AI が業務を続けながら自分で書き換えられます。たとえば「月末請求書の作成」を Skill として動かしていて、3 回繰り返すうちに「次回からはこのテンプレを使う」「この顧客はこの請求形式」と細部が固まってきたら、AI がその学習を SKILL.md に書き戻して、4 回目から自動で適用します。N8N のワークフローは、人が GUI を開いて編集する作業が発生します。
(d) コスト効率。N8N を自前で動かすなら、月 5 ドルくらいの DigitalOcean droplet と、初期設定時間が必要です。Claude Code は Pro / Max / Team / Enterprise のいずれかのプランがあれば、cron 1 行で十分に動きます。インフラを別建てしなくていいので、運用負荷も低いです。ラップトップを閉じている間も動かしたい場合は、Claude Code Routines という Anthropic 管理のクラウド実行機能 (研究プレビュー段階) も使えます。
要するに、AI モデル (シェフ) の能力は、Claude API でも Claude Code でも同じです。差がつくのは、その AI を動かす環境 (調理場) の設計です。N8N + 外部ツール + JSON config という構成と、Claude Code エコシステム内で完結する構成は、シェフが同じでも出来上がる料理が変わります。Claude Code は Skills と Subagents と Hooks と MCP と cron をひとつにまとめて、AI が業務文脈を持ったまま判断・実行できる調理場として設計されています。
技術寄りの読者向けに 1 段落補足します。複雑な業務 (たとえば メール仕分けの分類精度をもっと上げたい、顧客分析を専門化したい) は、Subagent (.claude/agents/<name>.md) で切り出せます。Subagent は専用の役割とツールセットを持った独立のエージェントで、Skill の中から呼び出せます。SessionStart hook を使うと、Claude Code 起動時にローカルの前回ログを要約して context にロードしておく、といった準備処理も自動化できます。Layer A の経営者には必須ではありませんが、Layer B の技術者がもう一段組みたいときの拡張ポイントです。
これで起動の話は片付きました。次は運用です。初日から完璧に動くわけではないので、最初の 30 日で何が起きるのかを見ていきます。
最初の 30 日は CLAUDE.md を毎日触る
初日から手放しで動かせるわけではないんですよね。最初の 1 週間は、CLAUDE.md のギャップが次々に表面化します。
メール下書きの言葉遣いが自分のトーンと微妙に違う。ブリーフィングが優先順位を外している。プロジェクト更新が、ある種類のタスクだけ漏らす。レポートが、自分が見たい数字を出していない。
これらは全部、CLAUDE.md に書いていなかった暗黙知です。
正直、最初の 1 週間は「これ本当に賢くなるんだろうか」と思いますよね。出力を見ながら、なんでこんな優先順位になるんだろう、なんでこのトーンで返信しようとするんだろう、と疑問が湧きます。それぞれが、CLAUDE.md に書いていない前提を AI が推測で埋めた結果です。
ひとつずつ気づくたびに、CLAUDE.md を 2 分くらい編集して埋めます。「メールでこの表現は使わない」「このプロジェクトは別カテゴリで扱う」「月次決算には XX 指標も入れる」。新人スタッフに業務を引き継ぐときに、最初の 1 週間は毎日「あ、この前提も伝えるの忘れてた」が出てくるのと同じ感覚です。
2 週間も続けると、出力の編集量が目に見えて減ってきます。読んで「ここだけ直す」が普通になります。
1 ヶ月もすると、ブリーフィングを読んで、ソースを確認せずに意思決定できるレベルまで精度が上がります。メールの下書きは、自分が体調の良い日に書く文章にかなり近くなります。週次レビューが、自分が手動で振り返っていたら見落としていたパターンを拾い始めます。
3 ヶ月もすると、たぶん手放せなくなります。半年もすると、最初のころの自分とは別の経営者をやっているみたいな感覚になります、たぶん。日次の事務オペレーションを手で回していた頃の自分の仕事の仕方は、もう思い出しにくくなります。
複利効果は最初から始まっています。ただ、目に見えるのは 1 ヶ月後で、手放せなくなるのは 3 ヶ月後です。最初の 1 週間で「精度が低い」と思って止めると、ここに辿り着けません。
CLAUDE.md は書いて終わりではなく、運用しながら毎日少しずつ厚みを増していくファイルです。最初の 30 日は、それを毎日触ると思っておくと、気が楽になります。
経営者が解放されると残る仕事
6 つのワークフローが動き始めると、経営者の朝が変わります。
メールを 1 通ずつ判断する代わりに、すでに分類されて下書きまで揃った状態を読んでレビューします。プロジェクトのステータスを Notion で追う代わりに、すでに更新済みの最新状態を読みます。週末に売上を集計する代わりに、すでにまとまった財務レポートを読みます。週初めに顧客の様子を心配する代わりに、すでに評価された AT RISK / ATTENTION NEEDED の一覧を読みます。
事務オペレーション層が、エージェントに移動した結果、経営者の手元に残る仕事は何でしょうか。
戦略の判断。顧客との関係構築。創造的な意思決定。チームの方針決め。新しいサービスの設計。価格戦略の見直し。市場の変化への対応。良い会社と素晴らしい会社の差を作る、判断業務だけが残ります。
これは経営者の仕事が変わる話です。事務オペレーションに溶けていた時間が、戦略と判断と関係構築に戻ります。
経営者が自社のオペレーション層をやっている時代は、Ambient Agent の設計で 1 ヶ月くらいで終わります。最初は morning-briefing の Skill を 1 つ書くところから始めます。週末に 1 時間使って 1 つの Skill を書く、を繰り返すと、2 ヶ月後には 6 つのワークフローが全部回っている状態に着地します。
メールに振り回される朝で止まるか、すでにコンパイル済みのブリーフィングを読む朝に切り替えるか。最初の Skill は morning-briefing 1 つから始められます。

自動化 (固定スクリプト) とエージェント (judgment + 業務文脈 + 行動) は別物。新規リード 1 通でやることが完全に違う
4 コンポーネントで成立する: Claude (判断) + CLAUDE.md (業務文脈) + MCP (ツール接続) + Skills + cron (起動 + 配線)

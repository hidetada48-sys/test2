Lowでは、テストを実行せずに「完了」と報告することがある

1つ目の指示は作業が長くなり費用も増えるので、ずっと入れておくより、席を離れて任せたい日だけ足すのがおすすめです。2つ目の指示は、公式の試験で、Maxのときの費用を品質を落とさずに約3分の1減らしました。

The Jevons Paradox, and why your bill never goes down
Jev is named after an economics rule from 1865.
William Stanley Jevons noticed that when steam engines started burning coal more efficiently, Britain did not burn less coal. It burned dramatically more. Efficiency made coal worth using in places nobody had bothered with, and total consumption exploded.
Tokens get cheaper every quarter. Your bill does not.
Every price drop opens a new place to put a model call, and the calls multiply faster than the price falls. The loop that ran a model three times last year runs it eleven times now, because each one got cheap enough to justify.
TypeSafe's bet is that the way out is not a cheaper model doing the same job. It is a different kind of model doing a job the first one was never built for.
01. Split - find the decisions, not the text
Every agent loop is made of three kinds of operation, and almost every stack collapses two of them into one.
Generation makes something that did not exist. Research, prose, code, an explanation of a failure. That needs a frontier LLM and always will.
Execution does the thing. Call the tool, write the file, stop after ten actions, hold the spending cap. That is code, it is free, and it never changes its mind.
Decision sits between them. Which worker runs next. How risky is this change. Should a person see it. The answer space is known before you ask, and the answer is going straight into an if statement.
I am going to build one thing across this article: a gate that reads a code change and decides whether it ships, goes back, or needs a human. I picked it because every team already has this decision and almost everyone either does it by hand or burns a frontier call on it.
The split has one rule and it fits in a line: if the operation creates text, it stays with the LLM. If it picks an option, scores a value, or answers yes or no, it goes to Jev.
That is Jev engineering. Everything below is how to wire it.
02. Playground - test one question before you write any code
Open the TypeSafe Playground and sign in. Access is by waitlist and people are getting approved the same day, but check before you plan around it.

Run it. Then flip migrations to true and run it again without changing anything else.
Watch the distribution move. That is the whole interaction, and five minutes here will teach you more than the docs.
What Jev actually is
TypeSafe calls it a System One model, after Kahneman's split between fast intuitive judgment and slow deliberate reasoning. The shortest accurate description is a semantic decision engine.
You send two things.
State - the text or JSON describing the situation right now. A diff summary. A support ticket. An order book snapshot. Whatever your code already has in memory.
Questions - the decisions you want made about that state, each one declaring its answer shape in advance.
What comes back is typed answers with probabilities. No prose. No JSON to repair. No fourth option the model invented because it felt like it.
The mental model that stuck across every write-up I read: an LLM maps state to text, Jev maps state to a decision distribution. Ordinary code branches on values it can compute. Jev branches on values it cannot.
if (diff.lines_added > 400) is something a computer can check.
if (this change goes beyond what the plan described) is not, and that gap is the whole reason you have been renting a chat model.

The single biggest mistake I made in my first hour was handing Jev the raw diff and hoping.
Everything computable stays in code. Line counts, file paths, test exit codes, whether a migration file exists, whether the diff strays outside the planned paths. None of that needs a model, and paying one to count is how you end up with a cheap model that costs more than the expensive one.

There are exactly three question types. That is the complete API surface.
Choice picks one option from a list you define, up to 255 of them, and returns a probability for every option plus a confidence.
Score places the state on an ordered scale you define. Define three rungs and the result runs 0 to 2, fractions included.
Noul answers a yes-or-no question by returning the probability that it is true. The name is odd; what matters is that you get a number between 0 and 1 your code can act on.

The accurate sentence is: Jev cannot break the declared output schema, but it can still be wrong.
Anyone selling you the shorter version has not shipped this into production.

Jev stops being useful the moment the answer space stops being known.
It cannot write, summarise, generate code, or explain itself. Rollout - without creating a new failure mode
A cheap model can still be expensive if its mistakes create retries, manual review, or incidents. Measure the whole workflow, not the token price.
The sequence that works:
pick one bounded, low-risk decision where you can name the possible answers
write the rubric before you call the model, and define what belongs in each option
collect real examples with expected answers, including the ambiguous and adversarial ones
run it in shadow mode beside your current logic, changing nothing
plot accuracy against confidence and set your thresholds from that curve, not from a blog post
automate the safest branch first, keep a human or a stronger model on the uncertain ones
pin the model version, and log the questions, criteria and thresholds so any change can be replayed
That last one is the discipline most teams skip. Your questions are part of your program. Version them, review them, and re-run your evaluation set whenever the model or the rubric changes.
I ran my gate in shadow mode for two days before it was allowed to block anything. It disagreed with me eleven times. Nine of those were my thresholds, not its judgment, and I would never have found that from a demo.
What actually changed
Jev is not interesting because it beats an LLM at writing. It refuses to write.
What it contributes is a model interface shaped like software instead of like conversation: fixed answer types, explicit uncertainty, parallel questions, and branching that stays in your code where you can review it.
The real finding is not the 7-second flight demo or the $0.08 classification run. It is how many expensive calls inside your agents never needed generation in the first place.
Let the LLM research, plan and write.
Let Jev route, score, approve and escalate.
Let code execute the decision.
That split changes the whole stack, and it survives whichever model eventually replaces Jev.
Most builders will keep spending frontier tokens on every yes, no, route and score, because it works and nobody is auditing the trace.
The ones who separate thinking from deciding will ship faster agents for a fraction of the bill.

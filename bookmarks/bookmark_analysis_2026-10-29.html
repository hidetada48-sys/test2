1. 人の確認時間を減らす仕組み（Claude Code チームのコードレビュー）

🛠 環境改善・向上

  • 1.P1 業務プログラムを直したあとに /code-review を流す：Claude Code に最初から入っている点検で、新しい会話の目で変更を読み、誤りを探します。例えば販売参謀の得意先別の売上集計プログラムを直したあと、/code-review と入力するだけで、集計の漏れや日付の境目の誤りを指摘してもらえます。読むだけの点検なので、承認が要る書き換えは発生しません。（元記事：1014-A1）
  • 2.P2 控え帳の叱責事例を「試験の問題集」にする：記事のチームは、過去の事故を問題集にし、点検の仕組みを変えるたびに全件で試しています。この環境では、承認の確認と測らない返答にはすでに試験があります（test-approval-gate.py・test-html-gate-exempt.py）。これを広げ、控え帳の事例（10/16 推測で3回答えた件、10/21 お尋ねの分け方を無視した件など）を1件1問にして、出す前の点検の仕組みを変えるたびに全件流すと、以前防げていた誤りの再発を防げます。（元記事：1014-A1）
  • 3.P2 業務リポジトリに REVIEW.md（点検で見る所の一覧）を置く：記事では、短い REVIEW.md に「この場所での誤りとは何か」を書き、/code-review がそれを読んで点検します。例えば「集計では、月の最後の日までデータが入っているか」「エクセルでは、合計と明細の数字が一致するか」「取引先名は正式な名前か」を書いておきます。同じ指摘が繰り返されたら、指摘する側ではなく元（CLAUDE.md・スキル・検査）で直す、というのが記事の考え方です。（元記事：1014-A1）
  • 4.P2 知りたい部分だけ解説資料を作ってもらう：記事のチームは、仕組み全体を誰も覚えていない前提で、知りたい部分の解説をその都度 Claude に作らせています。例えば「在庫の月末集計プログラムが、どの表のどの数字を使っているかを、専務向けに1枚で説明して」と頼めば、プログラム全体を読まなくても、直す前に要点をつかめます。（元記事：1014-A1）

📚 学習

  • 5.P2 公式ブログ「How the Claude Code team does code review」全文（約14分）：Claude Code のプログラムの約9割を Claude が書き、6〜9月に取り込んだ変更が2倍超、取り消し率が40%以上減った背景が学べます。確認の手厚さを危険度で分ける考え方（文書の直し＝人の承認なし、普通の変更＝1人、危険な所＝2人）、点検と直しの往復を3回までに抑える考え方、人の判断が残る所（作るべきかの判断・危険な所・証拠を読むこと・結果の責任）が書かれています。承認の決まりを見直すときの参考になります（今すぐ変える提案ではありません）。（元記事：1014-A1）

2. 「結果が良くなったか」を測る（成田悠輔氏の研究に学ぶ活用術）

🛠 環境改善・向上

  • 6.P1 依頼の前に4行（目的・入力・出力・確認方法）を書く：次に新しい集計や資料を頼むとき、最初にこの4行を添えます。運賃の月次照合なら、目的＝運送会社の請求額と自社の出荷記録の差を見つける、入力＝10月分の請求書（PDF）と出荷の一覧（エクセル）、出力＝差のある行だけを並べたエクセル1枚、確認方法＝請求書の合計額とエクセルの合計額が一致すること、となります。4行が書けない仕事は、まだ頼む段階ではないと判断できます。（元記事：1014-B1）
  • 7.P2 売上の増減を4つに分けて整理してもらう：販売参謀に売上の変化を尋ねるとき、①データで直接確かめられること ②原因の候補（未確定） ③比べにくくしている条件（同じ時期の値上げ・季節・新規の取引先など） ④次から記録すべき項目、の4つに分けるよう依頼し、「原因を断定できなければ『断定できない』と書く」を添えます。値上げの月と売上の増加が重なったとき、値上げが原因だと早合点するのを防げます。（元記事：1014-B1）
  • 8.P2 AIに任せた業務の「全体の時間」を記録する：記事は、測るべきは「作るまでの時間」でなく、直し・確認・作り直しを含めた全体の時間だとしています。日報アプリや月次集計など、Claude Code に任せた業務ごとに、案件台帳の各案件へ「直しの回数」「確認にかかった時間」を1行で残すと、「速くなった」ではなく「本当に楽になったか」を数字で判断できます。（元記事：1014-B1）

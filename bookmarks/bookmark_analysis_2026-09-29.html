② effort・モデル・コストの管理【6件】

🛠 環境改善・向上

  • 7.P1 settings.json の "effortLevel": "high" を見直す：Opus 5.5 は既定が medium。Opus 5 時代の high を持ち越すと「要らない深さで考えて、出力（いちばん高い部分）が増える」と複数の記事が指摘。案は「既定は medium、難しい作業のときだけ上げる」。注意：会話の途中で全体の effort を変えるとキャッシュ（読み直しを安くする仕組み）が効かなくなるので、変えるのは会話の最初か区切り（/clear の後）で。settings.json は両OS共通なので、変えるなら dotfiles 側で1回。（元記事：0929-B1, B3）
  • 8.P1 /skill-doctor と /mcp で「待機中の重さ」を測る：/skill-doctor は読み込まれているスキルごとの消費量と未使用スキルを出す（Claude Code 公式の機能として存在を確認済み。ただし元記事の「7割削減」は誇大表現）。この環境はMCP（外部サービスとつなぐ仕組み）が多い（playwright・jina・discord・Google Drive・basic-memory・context7 など）。公式ワークショップの「今日使わないMCPは /mcp で切る。待機中でもタダではない」をそのまま適用できる。（元記事：0908a-B1, 0920-C1）
  • 9.P1 /usage の数字を公式の計算ツールに入れて、自分の1作業あたりの費用を知る：公式ブログ「What a task costs on Opus 5.5」に計算ツールがある。キャッシュの当たり率が費用を最も大きく動かす（90%と96%で入力費が約1.6倍違う）。（元記事：0929-B2, B4）
  • 10.P2 サブエージェントにモデルを割り振る：いまの4エージェント（doc-verifier・equipment-history・my-info-extractor・seo-researcher）は、会話本体のモデルをそのまま使う。調べもの・抜き出し系（my-info-extractor・equipment-history）は安いモデルに下げ、判断が要る所だけ上位に残すと費用が下がる。エージェント定義の frontmatter（ファイル先頭の設定欄）に model を書けるかは公式ドキュメントで確認してから。（元記事：0902-A1, 0920-C1, 0908a-A1 の12項）
  • 11.P2 「作るのは低 effort、確かめるのは高 effort」の2段構え：Claude Code チームの実測では、effort を上げて増えるのは主に「検証とエッジケース（めったに起きない条件）のテスト」。同じ設計タスクで low 1分・max 28分。新しい用途の例：月次の Excel 集計スクリプトを作る時、作成は low で速く回し、完成品の突き合わせだけ high の別エージェントにやらせる。（元記事：0929-B1）

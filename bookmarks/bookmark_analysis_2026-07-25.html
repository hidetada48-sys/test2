AI社員化の段階論 ―― 焦って自動化しない

🛠 環境改善・向上

  • 1.P1 「業務単位」でスキル化する視点を持つ：記事3の核心は「AI社員ではなく業務単位で小さく作る」。抽象的な役割（AIマーケター等）ではなく「領収書ファイル名をルール通り整理するAI」のように狭く切る。→ 今後スキルを新設するときは skill-creator で作る前に「入力・出力・合格基準が1行で書けるか」を確認基準にする。書けない粒度のスキルは作らない、というルールをCLAUDE.mdの「新機能を作る前」節に追記できる。（元記事：3）

📚 学習

  • 2.P2 「暗黙知の言語化 → 型化 → 半自動化」の順番：チャットで勝ちパターンが固まった業務だけをClaude Code側（スキル・CLAUDE.md）に移す、という順序論。自分の既存スキル（note生成・ブックマーク分析等）が「チャットで何度も回して型が固まったもの」に対応しているか、逆算で検証する視点として学べる。（元記事：3）

Claude Code全機能マップ ―― 9レイヤーで棚卸し

🛠 環境改善・向上

  • 3.P1 レイヤー混同のセルフチェック：記事5の警告「本来CLAUDE.mdに書くべきをHookに書く／Permissionで止めるべきをSkillの文章でお願いしただけ」は、まさに設定を触る人が陥る罠。→ 今の自分の設定を「モデル/Tool/Agent/Skill/Plugin/Hook/Permission」の役割で1度棚卸しし、"文章でお願いしているだけの強制事項"がないか点検する。（元記事：5）
  • 4.P2 .claude/rules/ によるコンテキスト出し分け：CLAUDE.mdを場所別に分割し、触るファイルに応じて必要なルールだけ読み込む仕組み。実施済みメモでは「現状不要」と判断済みだが、CLAUDE.mdが肥大化してきた今、HTML化ルールやGitルールなど「特定作業時だけ効けばよいもの」を rules/ に切り出す再検討の価値がある。（元記事：5）

📚 学習

  • 5.P2 Advisor（第二意見）とFork の使い分け：Advisor＝メイン会話の全履歴を渡して「その判断どう思う？」と助言をもらう相談役、Fork＝会話まるごと引き継いで別案を調べる分身。Subagentとの違いを含め、重要判断前の使い分けとして押さえる。（元記事：5）
  • 6.P3 Checkpointはバックアップではない：Bashが変更したファイル・DB更新・Git Push・本番Deployは元に戻らない。だから区切りでのGitコミット（保存3点セット）が正しい、という裏付け。現運用の妥当性を確認できる知識。（元記事：5）

出力形式論 ―― Markdown から HTML へ

🛠 環境改善・向上

  • 7.P2 HTML出力の"活かし方"を一段深める：記事1は「コードレビューはカラフルなdiff、計画はインタラクティブなカンバン、プロンプト調整は最適化ツールとしてHTML化」と具体用途を挙げる。→ 現在のHTML化ルールは「回答をHTMLで返す」止まりだが、例えば新規に手続き比較表を色分けHTMLで出す、チェックリストを開閉式HTMLにするなど、静的変換の一歩先（インタラクティブ化）を試す余地がある。（元記事：1）

📚 学習

  • 8.P3 「編集しやすさ」の価値低下という論点：Markdownの利点＝手編集のしやすさが、AIが1000行を一括生成する時代には不要になった、という主張。トークン増・生成2〜4倍遅の代償を体験価値10倍が上回るか、は自分の用途で判断すべき論点として学ぶ。（元記事：1）

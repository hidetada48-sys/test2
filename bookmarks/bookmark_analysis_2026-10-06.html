今週の中心は、9月下旬に公開された新しいモデル（Sonnet 5.5・Opus 5.5）の使い分けと、費用を抑えるための設定の見直しです。あわせて、Claude Code 本体の新しい拡張機能（公式プラグイン「You should know」、改造の仕組み「Mods」）と、Skills（決まった仕事の手順書）を絞り込む考え方が取り上げられていました。

現在の環境の状況（照合の結果）：

  • Claude Code は 2.1.291（Sonnet 5.5 に対応する 2.1.284 以降）
  • 補助役のエージェント4つ（公式の照合・設備の履歴調べ・会話ログの抜き出し・記事の調査）は、すべて Sonnet を使う指定。つまり現在は自動で Sonnet 5.5 で動いています
  • 考える量（effort）の設定は、Opus 5.5 が「中」、旧 Opus 5 が「高」
  • 自作の Skills は16個、ほかにプラグイン由来のものが多数あります

1. 新しいモデルの使い分け（Sonnet 5.5／Opus 5.5／Fable 5.1）

🛠 環境改善・向上

  • 1.P1 公式ガイドに沿って、モデルと考える量の設定を点検させる：記事にある点検用の依頼文（「まず推奨だけ表示し、何も変更しない」で終わるもの）をそのまま Claude Code に渡すと、モデル指定のないエージェント、Sonnet 向けに固定された考える量、古いモデル向けの指示（「考えすぎるな」「怠けるな」等）を一覧で出してくれます。この環境では、補助役4つが Sonnet 5.5 で動いていること、旧 Opus 5 用の設定が残っていることが点検対象になります。変更は一覧を見てから決められます。（元記事：A-2）
  • 2.P2 補助役エージェントの考える量を仕事の重さで分ける：Sonnet 5.5 では考える量の段階が作り直されたため、旧来の設定をそのまま引き継がない方がよいとされています。目安は「範囲が決まった調べ物＝中」「難しい・長い作業＝高」「最高段階は効果を測ったときだけ」。例として、設備の履歴調べ（件数を数えるだけ）は「中」、公式ドキュメントとの照合（誤りを見つける）は「高」に分けると、費用と精度の釣り合いが取れます。（元記事：A-2）
  • 3.P2 「計画は Opus、実際の作業は Sonnet」の自動切り替えを試す：/model opusplan を選ぶと、計画を立てる段階は Opus 5.5、書く段階は Sonnet 5.5 に自動で分かれます。例えば、新しい集計表を作るとき「どういう表にするか」は Opus、「表を組み立てて数式を入れる」は Sonnet、と1つの設定で分担できます。ただし Opus 単独の方が安かった報告もあるため、同じ作業で費用を比べてから続けるか決めるのが確実です。（元記事：A-2 引用記事）
  • 4.P2 相談役として Fable 5.1 を付ける：/advisor fable を実行すると、作業は Opus 5.5 が続け、Fable 5.1 が「計画の前」「同じ誤りが繰り返したとき」「完了と言う前」の3回だけ口を挟みます。数字の集計のように、誤りを見落とすと後で手戻りが大きい仕事で効果が出やすい使い方です。記事は CLAUDE.md への規則追加や設定の書き換えまで勧めていますが、まずは1回の作業で試し、効果を確かめてから設定に残すのが安全です。（元記事：A-3）

📚 学習

  • 5.P2 Sonnet 5.5 の癖と抑え方：「頼んでいない物を作り始める」「調べずに記憶で答える」「低い設定だとテストを実行せずに完了と言う」などの癖と、それぞれを抑える一言（「案を出したらそこで止めて」「変わりやすい情報は検索で確かめて」「テストを実行して結果を見せて」）が学べます。表計算は「数式で組んで」と頼み、入力を1つ変えて結果が連動するか確かめる、という確認方法も実務に直結します。（元記事：A-2 引用記事）
  • 6.P3 「はい／いいえ」の判断に高いモデルを使わない考え方：文章を作る仕事は大きなモデル、選ぶ・判定するだけの仕事は判定専用の安いモデル、計算や件数の確認は普通のプログラム、と3つに分ける設計が学べます。「プログラムで正しく判定できることは、モデルに聞かない」という原則は、集計や照合の仕組みを作るときにそのまま使えます。（元記事：A-3 引用記事）

📡 情報収集

  • 7.P3 Haiku 5.5 の公開：数週間以内に公開予定とされています。件数の多い単純な仕分けを安く回せる可能性があるため、公開時に料金と性能を確認する価値があります。（元記事：A-2 引用記事）
  • 8.P3 判定専用モデル「Jev」（TypeSafe 社）：9月15日に公開。性能の数字は開発元の自己評価が中心で、第三者の検証はまだありません。実際の利用報告が出そろうまで様子を見ます。（元記事：A-3 引用記事）

2. Claude Code 本体の新しい拡張機能

🛠 環境改善・向上

  • 9.P1 公式プラグイン「You should know」を有効にする：/plugin enable cc-plugin-you-should-know@builtin の1行で有効になります。別のエージェントが作業報告を横で読み、「再試行を足したが二重請求の恐れがある」程度の重大な落とし穴だけを知らせ、「了解・会話で相談・閉じる」の3択でその場で返せます。長い作業報告を最後まで読まなくても、危ない1行を見落としにくくなります。例として、取引先別の売上集計を作り直させたとき「金額0以下の行を除外した結果、返品分が消えている」といった注意だけを先に受け取れる、という使い方が想定できます。（元記事：B-1）
  • 10.P2 「Mods」で画面や動き方を自分向けに変える：Claude Code の見た目や動き方を自分で書き換えられる仕組みです。この環境では、作業中の画面の端に「今日の未完了の定例業務の件数」を常に表示する、といった使い方が考えられます。投稿は概要のみのため、作る前に公式ドキュメントで手順を確認します。（元記事：B-2）

3. Skills（決まった仕事の手順書）の絞り込み

🛠 環境改善・向上

  • 11.P2 Skills の棚卸し：記事は「入れすぎると呼ばれ方がずれる。8個を超えると誤って呼ばれることが増えた」としています。この環境は自作16個に加え、同じ名前の Skills が2系統ある物（問題集の作成・模擬テスト・答えの検証・Skills作成が、自作版とプラグイン版で重複）があります。重複している4組のうち使っていない方を外すと、呼び間違いが減る見込みです。（元記事：C-1）
  • 12.P2 Skills の説明文の書き方を見直す：自動で呼ばれるかは説明文で決まります。「大事な言葉を先頭に置く」「日本語の言葉を前に書く」「長すぎない」が要点です。この環境の説明文は長めの物が多いため、呼ばれにくい Skills があれば、説明文の先頭を「どんなときに使うか」の日本語にそろえます。（元記事：C-1）

📚 学習

  • 13.P3 Skills は「3つの仕事の分野 × 3〜4個」に絞る考え方：書類作成・調べ物・自動化のように分野を分け、2週間使っていない物は外す、という整理の仕方が学べます。8個という数字は投稿者の経験値であり、公式の基準ではない点に注意が必要です。（元記事：C-1）

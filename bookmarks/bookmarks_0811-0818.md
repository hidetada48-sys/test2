しかし、文章は方針であり、物理的な制限ではありません。
本当に本番環境へ書き込ませたくないなら、
読み取り専用の認証情報を使う
書き込みツールを渡さない
対象ディレクトリを制限する
Hookで危険操作をブロックする
実行環境を分離する
ネットワークの接続先を限定する
必要があります。
24時間動くエージェントにとって、文章だけの禁止は弱い設計です。
守られなければ困るルールは、プロンプトではなく権限・コード・実行環境で守る。
これが基本です。
理由4：失敗したときの挙動を決めていない
正常に動く手順だけを考え、失敗時の行動を決めていないエージェントは、必ずどこかで止まります。
例えば、ニュース取得APIが失敗した場合。
すぐ再試行するのか
何秒待つのか
最大何回試すのか
一部だけ取得できたら続けるのか
人間へ通知するのか
次回の実行へ持ち越すのか
を事前に決める必要があります。
悪い設計は、次です。
失敗したら、成功するまで再試行してください。
良い設計は、次です。
一時的な通信エラーのみ再試行する。
待機時間は30秒、2分、10分とし、
最大3回まで実行する。

認証エラー、権限不足、入力不備は再試行せず停止する。

3回失敗した場合は、
ジョブ状態をfailedへ変更し、
エラー内容、最後に成功した工程、
再開方法をSlackへ通知する。
AIに判断させる前に、エラーの種類と停止条件を決めます。
理由5：AIを増やせば速くなると思う
リサーチ担当、構成担当、執筆担当、編集担当、検証担当。
役割を分けると、立派なAI組織に見えます。
しかし、エージェントを増やすと、次のコストも増えます。
引き継ぎ
状態同期
重複作業
出力形式の調整
コンテキストの複製
権限管理
失敗箇所の追跡
実行コスト
競合状態
独立して並列化できる仕事なら、複数エージェントは有効です。
一方、前工程の結果を待つ必要がある仕事を無理に分けると、引き継ぎコストの方が大きくなります。
最初は、1体のエージェントが小さなワークフローを順番に進める設計で十分です。
複数エージェントへ分けるのは、次の条件を満たす場合だけにします。
作業が明確に独立している
同時に進める意味がある
入出力形式が固定されている
失敗した作業だけ再実行できる
権限を役割ごとに分離できる
同じデータを同時更新しない
コスト増加に見合う時間短縮がある
■ 壊れにくいAIエージェントを作る7つの設計原則
原則1：AIへ渡すのは「判断」だけにする
すべてをAIへ任せると、自由度が高すぎて結果が安定しません。
まず、処理を2種類へ分けます。
決定的な処理
同じ入力なら、同じ結果になってほしい作業です。
APIからデータを取得する
日付で絞り込む
重複を削除する
JSONを保存する
Slackへ通知する
ファイル名を変更する
数値を集計する
スキーマを検証する
これらは、コードやワークフローで実行します。
非決定的な処理
文脈を読み、判断する必要がある作業です。
重要なニュースを選ぶ
読者に合う切り口を考える
問い合わせの意図を分類する
コードの問題点を分析する
返信文を作成する
複数案から最適な案を選ぶ
ここだけをAIへ渡します。
例えば、AIニュース収集なら次の構造です。
[コード]
RSS・APIから記事を取得
↓
[コード]
日付、URL、タイトルで重複削除
↓
[AI]
重要度と読者への関連性を評価
↓
[AI]
上位5件を要約
↓
[コード]
JSONスキーマを検証
↓
[コード]
Notionへ保存
↓
[コード]
Slackへ通知
AIの担当範囲が狭いほど、テストと改善が簡単になります。
原則2：各工程に「完了条件」を持たせる
「ニュースを調べる」のような曖昧なタスクは、いつ終わったのか判定できません。
工程ごとに、入力、出力、完了条件を定義します。
リサーチ工程
入力：
対象媒体：5件
対象期間：過去24時間
最大取得件数：100件
完了条件：
指定した5媒体を確認済み
過去24時間の記事だけを対象
URLとタイトルの重複を除去済み
最低10件を取得
各記事に取得時刻と出典URLがある
要約工程
出力：
{
  "selected_articles": [
    {
      "title": "",
      "source_url": "",
      "importance_score": 0,
      "reason": "",
      "summary": ""
    }
  ]
}
完了条件：
上位5件を選定
各要約は200文字以内
事実と推測を分離
元URLを保持
JSONスキーマへ適合
重要度の理由を記載
完了条件があれば、AI自身の「できました」ではなく、システム側で判定できます。
原則3：状態を外部へ保存する
24時間運用では、セッションが落ちることを前提にします。
状態を保存していなければ、再起動するたびに最初からやり直します。
最低限、次を保存します。
{
  "job_id": "weekly-content-2026-W31",
  "workflow_version": "1.0.0",
  "status": "running",
  "current_step": "draft_review",
  "completed_steps": [
    "source_collection",
    "deduplication",
    "topic_selection",
    "draft_generation"
  ],
  "pending_steps": [
    "draft_review",
    "human_approval",
    "publication"
  ],
  "retry_count": 1,
  "idempotency_key": "weekly-content-2026-W31",
  "last_error": null,
  "cost_usd": 1.42,
  "updated_at": "2026-07-30T09:00:00+09:00"
}
保存先は、用途に応じて選べます。
小規模：JSON、SQLite
チーム運用：PostgreSQL
長時間ワークフロー：Trigger.devなど
クラウドエージェント：サービス側のセッション・イベント履歴
重要なのは、会話を再現することではありません。
仕事の現在地を復元できることです。
原則4：重複実行を「冪等性」で防ぐ
24時間運用では、同じイベントが複数回来ることがあります。
例えば、
Webhookが再送される
タイムアウトしたため再実行される
人間が誤って二度起動する
スケジュールとAPI呼び出しが重なる
このとき、同じ投稿を二度公開したり、同じ顧客へ二度メールを送ったりしてはいけません。
そこで、各ジョブに一意のidempotency_keyを持たせます。
news-summary:2026-07-30
invoice-reminder:customer-123:2026-07
x-post:campaign-88:post-03
処理開始前に、次を確認します。
このidempotency_keyのジョブが
completedなら、何もしない。
runningなら、既存ジョブの状態を返す。
failedなら、再開条件を確認する。
未作成なら、新規ジョブとして開始する。
特に、送信、公開、課金、削除のような副作用がある処理には必須です。
原則5：リトライに上限と種類を持たせる
リトライは便利ですが、無制限にすると最も危険な機能になります。
エラーを、少なくとも次の3種類へ分けます。
再試行してよいエラー
一時的なネットワーク障害
レート制限
サービスの一時停止
タイムアウト
5xxエラー
人間の確認が必要なエラー
入力データの意味が曖昧
想定外の形式
重要な仕様の不一致
成果物が品質基準を満たさない
AIの判断が低信頼
再試行してはいけないエラー
認証情報が無効
権限不足
対象が存在しない
禁止された操作
予算上限超過
入力値が不正
さらに、次を必ず決めます。
最大試行回数
待機時間
累計コスト上限
失敗時の通知先
再開方法
一時エラーのみ最大3回再試行する。
待機時間は30秒、2分、10分と増やす。
同じツール呼び出しが5分以内に3回連続した場合は停止する。
累計コストが3ドルを超えた場合も停止する。
停止時は、エラー、最後の成功工程、再開方法をSlackへ通知する。
原則6：権限は最小限から始める
24時間動くエージェントは、人間が見ていない時間にも操作します。
したがって、対話型AIより厳しい権限設計が必要です。
最初から渡してはいけない権限があります。
本番データの削除
無制限の外部送信
任意のシェル実行
全リポジトリへの書き込み
決済や購入
SNSへの無承認投稿
機密情報への広範なアクセス
段階的に権限を広げます。
段階1：読み取りのみ
データを取得し、下書きを保存する。
段階2：限定された書き込み
専用フォルダ、専用ブランチ、下書きチャンネルだけに書き込む。
段階3：承認後の外部操作
人間が確認した後で、公開・送信・マージする。
段階4：条件付き自動実行
十分な運用実績があり、ロールバック可能な処理だけを自動化する。
最初から完全自動を目指すより、安全な半自動を積み上げた方が、結果的に早く本番へ到達します。
原則7：Hookと監視で「守る・見る・止める」を仕組みにする
Claude CodeのHooksは、ライフサイクル上の特定イベントで、自動処理を実行できる仕組みです。
例えば、
ツール実行前
ツール実行後
ファイル編集後
セッション開始時
セッション終了時
タスク完了時
などに処理を挟めます。
Hookの価値は、モデルへお願いするのではなく、決定的な処理として実行できる点です。
例1：危険なコマンドを止める
rm -rf、本番DBへの直接操作、強制pushなどを検知してブロックします。
例2：編集後に検証する
ファイル編集後にformatter、lint、型チェック、テストを自動実行します。
例3：同一処理の連続実行を検知する
短時間に同じツール呼び出しが繰り返されたら停止・通知します。
例4：作業記録を保存する
タスク完了時に、実行内容、変更ファイル、検証結果をログへ保存します。
例5：外部操作の前に承認を求める
送信、公開、削除などの前に処理を停止し、人間へ確認します。
さらに、最低限次を記録します。
開始時刻
入力データ
使用したツール
出力結果
エラー
リトライ回数
実行コスト
承認者
状態遷移
運用で重要なのは、「成功したか」だけではありません。
人間が後から理由を説明できることです。

■ 24時間動かす方法は、用途によって選ぶ
設計ができたら、次に実行環境を選びます。
すべてを一つの方法で解決しようとしないことが重要です。
1．/loop｜その場で試す短時間の繰り返し
Claude Codeの/loopは、開いているセッション内でプロンプトを定期実行するための方法です。
/loop 10m PRの状態を確認し、完了したら結果を要約してください
向いている用途：
デプロイ完了の監視
ビルド状況の確認
PRやIssueの短時間ポーリング
開発中の一時的な監視
自動化の試作
向いていない用途：
PCを閉じても継続したい処理
数週間以上の永続運用
厳密な時刻が必要な基幹処理
完全無人の本番業務
/loopは、セッションが開いている間に使う軽量なスケジューリングです。
現在の公式ドキュメントでは、定期タスクは作成から7日で終了します。永続運用にはRoutinesやDesktopのスケジュール済みタスクなどが案内されています。
/loopは、本番運用の完成形ではなく、短時間で挙動を確認する実験環境として使うのが適しています。
2．Claude Routines｜PCを閉じても動く定期・イベント実行
Claude Routinesは、Anthropicが管理するクラウド環境でClaude Codeの処理を実行する仕組みです。
スケジュール
API呼び出し
GitHubイベント
などをトリガーとして利用できます。
PCを閉じても動作するため、次のような処理に向いています。
毎朝の情報収集
Issueの定期整理
GitHub PRのレビュー
デプロイ後の検証
ドキュメント差分の監視
Slackや外部サービスへの通知
Routinesは無人で実行されるため、実行中に承認ダイアログへ答えることはできません。
そのため、
接続するリポジトリ
ブランチへのpush権限
使用するコネクタ
ネットワークアクセス
環境変数
外部サービスの権限
を必要最小限へ絞る必要があります。
Routinesは現在リサーチプレビューで、挙動や制限は変更される可能性があります。定期実行の最小間隔は1時間です。
より短い間隔で監視するなら/loop、イベントへ即時反応するならAPIまたはGitHubトリガーを検討します。
3．Modal・Trigger.devなど｜決まったワークフローをクラウドで回す
AIの判断がほとんど不要な場合は、Claude Codeを常時動かす必要はありません。
例えば、
APIからデータを取得
形式を変換
データベースへ保存
通知を送信
という処理は、通常のサーバーレス基盤や永続ワークフロー基盤で十分です。
Modalが向いている場面
Python中心
バッチ処理
データ処理
必要なときだけ計算資源を使いたい
AI以外の処理が中心
Trigger.devが向いている場面
TypeScript中心
長時間ワークフロー
ステップ単位の再試行
ジョブ状態の追跡
イベント駆動処理
AI判断が必要なら、その工程だけAPIまたはAgent SDKを呼びます。
ワークフロー全体をAIにするのではなく、AIを一つの処理部品として組み込むのがポイントです。
4．Claude Agent SDK｜自分のアプリ内でエージェントを動かす
Claude Agent SDKは、Claude Codeを支えるエージェントループやツール利用を、自分のPython・TypeScriptアプリケーションへ組み込むためのSDKです。
向いている用途：
自社サービスへエージェントを組み込む
独自UIからClaudeを動かす
自分のインフラでジョブを管理する
ツールや権限を細かく制御する
複雑なエージェントワークフローをコード化する
Agent SDKは自由度が高い一方で、周辺の運用は自分で設計します。
実行環境
スケジューリング
データ保存
キュー
監視
リトライ
シークレット管理
コスト制御
「SDKを使えば24時間動く」のではありません。
SDKは、エージェントの頭脳と実行ループを提供します。
24時間運用に必要な身体と運用体制は、自分で作ります。
5．Managed Agents｜実行基盤の管理を減らす
Managed Agentsは、Anthropicがエージェントの実行基盤を提供するサービスです。
モデル、システムプロンプト、ツール、MCP、Skillsなどを定義し、Anthropic管理またはセルフホスト型のサンドボックスでセッションを実行できます。
向いている用途：
長時間・非同期エージェントを動かしたい
自前でサンドボックスを管理したくない
セッションやイベント履歴を保存したい
APIからエージェントを起動したい
再利用可能なエージェント設定を持ちたい
Managed Agentsは、長時間実行、ステートフルなセッション、イベント履歴の永続化などを提供します。
一方で現在はベータ版であり、データ保持やコンプライアンス要件も含めて確認が必要です。
Agent SDKとの違いは、誰が実行基盤を管理するかです。
Agent SDK：自分のプロセスとインフラで動かす
Managed Agents：Anthropic管理またはセルフホスト環境を利用する
細かい制御が必要ならAgent SDK。
基盤管理を減らし、エージェント開発へ集中したいならManaged Agentsが候補になります。

■ 最初のAIエージェントは「1時間・1体・1業務」で作る
初心者が最初から作るべきなのは、24時間完全自動で働く巨大なAI組織ではありません。
次の条件で始めます。
実行時間：1時間以内
エージェント数：1体
対象業務：1つ
外部書き込み：下書きのみ
再試行：最大2〜3回
人間の承認：公開前に必須
例えば、AIニュース収集なら次です。
第1段階
毎朝ニュースを取得し、候補をSlackへ送る。
AI判断なし。
第2段階
AIが重要度を付け、上位5件を要約する。
外部公開はしない。
第3段階
AIがX投稿の下書きを作る。
人間が確認する。
第4段階
承認された投稿だけ、予約投稿へ登録する。
第5段階
十分な運用実績ができた一部だけ、自動実行する。
この順番なら、失敗した工程を特定できます。
いきなり全自動にすると、取得、判断、生成、公開のどこで壊れたのか分かりません。
■ 本番投入前に確認する15項目
1ジョブに一意のIDがある
二重実行を防止できる
現在の状態を外部保存している
途中から再開できる
